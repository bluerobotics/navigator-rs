21//! Interface for the UART peripherals and any USB to serial adapters.
22//!
23//! RPPAL controls the Raspberry Pi's UART peripherals through the `ttyAMA0`
24//! (PL011) and `ttyS0` (mini UART) character devices. USB to serial adapters
25//! are controlled using the `ttyUSBx` and `ttyACMx` character devices.
26//!
27//! ## UART peripherals
28//!
29//! The Raspberry Pi's BCM283x SoC features two UART peripherals.
30//! `/dev/ttyAMA0` represents the PL011 UART, which offers a full set of
31//! features. `/dev/ttyS0` represents an auxiliary peripheral that's referred
32//! to as mini UART, with limited capabilities. More details on the differences
33//! between the PL011 and mini UART can be found in the official Raspberry Pi
34//! [documentation].
35//!
36//! On earlier Raspberry Pi models without Bluetooth, `/dev/ttyAMA0` is
37//! configured as a Linux serial console. On more recent models with Bluetooth,
38//! `/dev/ttyAMA0` is connected to the Bluetooth
39//! module, and `/dev/ttyS0` is used as a serial console instead. Due to the
40//! limitations of `/dev/ttyS0` and the requirement for a fixed core frequency,
41//! in most cases you'll want to use `/dev/ttyAMA0` for serial communication.
42//!
43//! By default, TX (outgoing data) is tied to BCM GPIO 14 (physical pin 8) and
44//! RX (incoming data) is tied to BCM GPIO 15 (physical pin 10). You can move
45//! these lines to different GPIO pins using the `uart0` and `uart1` overlays,
46//! but the alternative pin options aren't exposed through the GPIO header on
47//! any of the current Raspberry Pi models. They are only available on the
48//! Compute Module's SO-DIMM pads.
49//!
50//! ## Configure `/dev/ttyAMA0` for serial communication (recommended)
51//!
52//! Disable the Linux serial console by either deactivating it through
53//! `sudo raspi-config`, or manually removing the parameter
54//! `console=serial0,115200` from `/boot/cmdline.txt`.
55//!
56//! Remove any lines containing `enable_uart=0` or `enable_uart=1` from
57//! `/boot/config.txt`.
58//!
59//! On Raspberry Pi models with a Bluetooth module, an extra step is required
60//! to either disable Bluetooth or move it to `/dev/ttyS0`, so `/dev/ttyAMA0`
61//! becomes available for serial communication.
62//!
63//! To disable Bluetooth, add `dtoverlay=pi3-disable-bt` to `/boot/config.txt`.
64//! You'll also need to disable the service that initializes Bluetooth with
65//! `sudo systemctl disable hciuart`.
66//!
67//! To move the Bluetooth module to `/dev/ttyS0`, instead of disabling it with
68//! the above-mentioned steps, add `dtoverlay=pi3-miniuart-bt` and
69//! `core_freq=250` to `/boot/config.txt`.
70//!
71//! Remember to reboot the Raspberry Pi after making any changes.
72//!
73//! ## Configure `/dev/ttyS0` for serial communication
74//!
75//! If you prefer to leave the Bluetooth module connected to `/dev/ttyAMA0`,
76//! you can configure `/dev/ttyS0` for serial communication instead.
77//!
78//! Disable the Linux serial console by either deactivating it through
79//! `sudo raspi-config`, or manually removing the parameter
80//! `console=serial0,115200` from `/boot/cmdline.txt`.
81//!
82//! Add the line `enable_uart=1` to `/boot/config.txt` to enable serial
83//! communication on `/dev/ttyS0`, which also sets a fixed core frequency.
84//!
85//! Remember to reboot the Raspberry Pi after making any changes.
86//!
87//! ## USB to serial adapters
88//!
89//! In addition to controlling the hardware UART peripherals, [`Uart`] can
90//! also be used for USB to serial adapters. Depending on the type of
91//! device, these can be accessed either through `/dev/ttyUSBx` or
92//! `/dev/ttyACMx`, where `x` is an index starting at `0`. The numbering is
93//! based on the order in which the devices are discovered by the kernel.
94//!
95//! When you have multiple USB to serial adapters connected at the same time,
96//! you can uniquely identify a specific device by searching for the relevant
97//! symlink in the `/dev/serial/by-id` directory, or by adding your own
98//! `udev` rules.
99//!
100//! Support for automatic software (XON/XOFF) and hardware (RTS/CTS) flow
101//! control for USB to serial adapters depends on the USB interface IC on the
102//! device, and the relevant Linux driver. Some ICs use an older,
103//! incompatible RTS/CTS implementation, sometimes referred to as legacy or
104//! simplex mode, where RTS is used to indicate data is about to be
105//! transmitted, rather than to request the external device to resume its
106//! transmission.
107//!
108//! ## Hardware flow control
109//!
110//! The RTS/CTS hardware flow control implementation supported by [`Uart`]
111//! and used by the Raspberry Pi's UART peripherals requires RTS on one
112//! device to be connected to CTS on the other device. The RTS signal is
113//! used to request the other device to pause or resume its transmission.
114//!
115//! Some devices use an older, incompatible RTS/CTS implementation, sometimes
116//! referred to as legacy or simplex mode, where RTS is connected to RTS, and
117//! CTS to CTS. The RTS signal is used to indicate data is about to be
118//! transmitted. [`Uart`] is not compatible with this implementation.
119//! Connecting the Raspberry Pi's RTS and CTS pins incorrectly could damage
120//! the Pi or the external device.
121//!
122//! When [`Uart`] is controlling a UART peripheral, enabling hardware flow
123//! control will also configure the RTS and CTS pins. On Raspberry Pi models
124//! with a 40-pin GPIO header, RTS is tied to BCM GPIO 17 (physical pin 11)
125//! and CTS is tied to BCM GPIO 16 (physical pin 36). RTS and CTS aren't
126//! available on models with a 26-pin header, except for the Raspberry Pi B
127//! Rev 2, which exposes RTS and CTS through its unpopulated P5 header with
128//! RTS on BCM GPIO 31 (physical pin 6) and CTS on BCM GPIO 30 (physical pin
129//! 5).
130//!
131//! The RTS and CTS pins are reset to their original state when [`Uart`] goes
132//! out of scope. Note that `drop` methods aren't called when a process is
133//! abnormally terminated, for instance when a user presses <kbd>Ctrl</kbd> +
134//! <kbd>C</kbd> and the `SIGINT` signal isn't caught, which prevents [`Uart`]
135//! from resetting the pins. You can catch those using crates such as
136//! [`simple_signal`].
137//!
138//! ## Troubleshooting
139//!
140//! ### Permission denied
141//!
142//! If [`new`] or [`with_path`] returns an `io::ErrorKind::PermissionDenied`
143//! error, make sure the file permissions for the specified device are correct,
144//! and the current user is a member of the group that owns the device, which is
145//! usually either `dialout` or `tty`.
146//!
147//! [documentation]: https://www.raspberrypi.org/documentation/configuration/uart.md
148//! [`simple_signal`]: https://crates.io/crates/simple-signal
149//! [`Uart`]: struct.Uart.html
150//! [`new`]: struct.Uart.html#method.new
151//! [`with_path`]: struct.Uart.html#method.with_path

186/// Errors that can occur when accessing the UART peripheral.
187#[derive(Debug)]
188pub enum Error {
189    /// I/O error.
190    Io(io::Error),
191    /// GPIO error.
192    Gpio(gpio::Error),
193    /// Invalid or unsupported value.
194    InvalidValue,
195}
196
197impl fmt::Display for Error {
198    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
199        match *self {
200            Error::Io(ref err) => write!(f, "I/O error: {}", err),
201            Error::Gpio(ref err) => write!(f, "GPIO error: {}", err),
202            Error::InvalidValue => write!(f, "Invalid or unsupported value"),
203        }
204    }
205}
206
207impl error::Error for Error {}
208
209impl From<io::Error> for Error {
210    fn from(err: io::Error) -> Error {
211        Error::Io(err)
212    }
213}
214
215impl From<gpio::Error> for Error {
216    fn from(err: gpio::Error) -> Error {
217        Error::Gpio(err)
218    }
219}
220
221impl From<system::Error> for Error {
222    fn from(_err: system::Error) -> Error {
223        Error::Gpio(gpio::Error::UnknownModel)
224    }
225}

230/// Parity bit modes.
231///
232/// The parity bit mode determines how the parity bit is calculated.
233///
234/// `None` omits the parity bit. `Even` and `Odd` count the total number of
235/// 1-bits in the data bits. `Mark` and `Space` always set the parity
236/// bit to `1` or `0` respectively.
237#[derive(Debug, PartialEq, Eq, Copy, Clone)]
238pub enum Parity {
239    /// No parity bit.
240    None,
241    /// Even parity.
242    Even,
243    /// Odd parity.
244    Odd,
245    /// Sets parity bit to `1`.
246    Mark,
247    /// Sets parity bit to `0`.
248    Space,
249}
250
251impl fmt::Display for Parity {
252    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
253        match *self {
254            Parity::None => write!(f, "None"),
255            Parity::Even => write!(f, "Even"),
256            Parity::Odd => write!(f, "Odd"),
257            Parity::Mark => write!(f, "Mark"),
258            Parity::Space => write!(f, "Space"),
259        }
260    }
261}

263/// Parity check modes.
264///
265/// The parity check mode determines how parity errors are handled.
266#[derive(Debug, PartialEq, Eq, Copy, Clone)]
267pub enum ParityCheck {
268    /// Ignores parity errors.
269    None,
270    /// Removes bytes with parity errors from the input queue.
271    Strip,
272    /// Replaces bytes with parity errors with a `0` byte.
273    Replace,
274    /// Marks bytes with parity errors with a preceding `255` and `0` byte.
275    ///
276    /// Actual `255` bytes are replaced with two `255` bytes to avoid confusion
277    /// with parity errors.
278    Mark,
279}
280
281impl fmt::Display for ParityCheck {
282    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
283        match *self {
284            ParityCheck::None => write!(f, "None"),
285            ParityCheck::Strip => write!(f, "Strip"),
286            ParityCheck::Replace => write!(f, "Replace"),
287            ParityCheck::Mark => write!(f, "Mark"),
288        }
289    }
290}

313/// Control signal status.
314pub struct Status {
315    tiocm: c_int,
316}
317
318impl Status {
319    /// Returns `true` if RTS is active.
320    ///
321    /// RTS (active low) is controlled by [`Uart`]. An active signal indicates
322    /// [`Uart`] is ready to receive more data.
323    ///
324    /// [`Uart`]: struct.Uart.html
325    pub fn rts(&self) -> bool {
326        self.tiocm & TIOCM_RTS > 0
327    }
328
329    /// Returns `true` if CTS is active.
330    ///
331    /// CTS (active low) is controlled by the external device. An active signal
332    /// indicates the external device is ready to receive more data.
333    pub fn cts(&self) -> bool {
334        self.tiocm & TIOCM_CTS > 0
335    }
336
337    /// Returns `true` if DTR is active.
338    ///
339    /// DTR (active low) is controlled by [`Uart`]. When communicating with a
340    /// modem, an active signal is used to place or accept a call. An inactive
341    /// signal causes the modem to hang up. Other devices may use DTR and DSR
342    /// for flow control.
343    ///
344    /// DTR is not supported by the Raspberry Pi's UART peripherals,
345    /// but may be available on some USB to serial adapters.
346    ///
347    /// [`Uart`]: struct.Uart.html
348    pub fn dtr(&self) -> bool {
349        self.tiocm & TIOCM_DTR > 0
350    }
351
352    /// Returns `true` if DSR is active.
353    ///
354    /// DSR (active low) is controlled by the external device. When
355    /// communicating with a modem, an active signal indicates the modem is
356    /// ready for data transmission. Other devices may use DTR and DSR for flow
357    /// control.
358    ///
359    /// DSR is not supported by the Raspberry Pi's UART peripherals,
360    /// but may be available on some USB to serial adapters.
361    pub fn dsr(&self) -> bool {
362        self.tiocm & TIOCM_DSR > 0
363    }
364
365    /// Returns `true` if DCD is active.
366    ///
367    /// DCD (active low) is controlled by the external device. When
368    /// communicating with a modem, an active signal indicates a connection is
369    /// established.
370    ///
371    /// DCD is not supported by the Raspberry Pi's UART peripherals,
372    /// but may be available on some USB to serial adapters.
373    pub fn dcd(&self) -> bool {
374        self.tiocm & TIOCM_CAR > 0
375    }
376
377    /// Returns `true` if RI is active.
378    ///
379    /// RI (active low) is controlled by the external device. When
380    /// communicating with a modem, an active signal indicates an incoming
381    /// call.
382    ///
383    /// RI is not supported by the Raspberry Pi's UART peripherals,
384    /// but may be available on some USB to serial adapters.
385    pub fn ri(&self) -> bool {
386        self.tiocm & TIOCM_RNG > 0
387    }
388}

390impl fmt::Debug for Status {

392        f.debug_struct("Status")
393            .field("rts", &self.rts())

396            .field("dsr", &self.dsr())
397            .field("dcd", &self.dcd())
398            .field("ri", &self.ri())
399            .finish()
400    }
401}

420/// Provides access to the Raspberry Pi's UART peripherals and any USB to
421/// serial adapters.
422///
423/// The `embedded-hal` [`serial::Read`], [`serial::Write`] and [`blocking::serial::Write`] trait
424/// implementations for `Uart` can be enabled by specifying the optional `hal` feature in the
425/// dependency declaration for the `rppal` crate.
426///
427/// [`serial::Read`]: ../../embedded_hal/serial/trait.Read.html
428/// [`serial::Write`]: ../../embedded_hal/serial/trait.Write.html
429/// [`blocking::serial::Write`]: ../../embedded_hal/blocking/serial/trait.Write.html
430#[derive(Debug)]
431pub struct Uart {
432    inner: UartInner,
433}
434
435impl Uart {
436    /// Constructs a new `Uart`.
437    ///
438    /// `new` attempts to identify the UART peripheral tied to BCM GPIO 14 and
439    /// 15, and then calls [`with_path`] with the appropriate device path.
440    ///
441    /// [`with_path`]: #method.with_path
442    pub fn new(baud_rate: u32, parity: Parity, data_bits: u8, stop_bits: u8) -> Result<Uart> {
443        Self::with_path("/dev/serial0", baud_rate, parity, data_bits, stop_bits)
444    }
445
446    /// Constructs a new `Uart` connected to the serial character device
447    /// specified by `path`.
448    ///
449    /// `with_path` can be used to connect to either a UART peripheral or a USB
450    /// to serial adapter.
451    ///
452    /// When a new `Uart` is constructed, the specified device is configured
453    /// for non-canonical mode which processes input per character, ignores any
454    /// special terminal input or output characters and disables local echo. DCD
455    /// is ignored, all flow control is disabled, and the input and output queues
456    /// are flushed.
457    pub fn with_path<P: AsRef<Path>>(
458        path: P,
459        baud_rate: u32,
460        parity: Parity,
461        data_bits: u8,
462        stop_bits: u8,
463    ) -> Result<Uart> {
464        // Follow symbolic links
465        let path = fs::canonicalize(path)?;
466
467        // Check if we're using /dev/ttyAMA0 or /dev/ttyS0 so we can set the
468        // correct RTS/CTS pin modes when needed.
469        let rtscts_mode = if let Some(path_str) = path.to_str() {
470            match path_str {
471                "/dev/ttyAMA0" => Some((GPIO_RTS_MODE_UART0, GPIO_CTS_MODE_UART0)),
472                "/dev/ttyS0" => Some((GPIO_RTS_MODE_UART1, GPIO_CTS_MODE_UART1)),
473                _ => None,
474            }
475        } else {
476            None
477        };
478
479        let device = OpenOptions::new()
480            .read(true)
481            .write(true)
482            .custom_flags(O_NOCTTY | O_NONBLOCK)
483            .open(path)?;
484
485        let fd = device.as_raw_fd();
486
487        // Enables character input mode, disables echoing and any special
488        // processing
489        termios::set_raw_mode(fd)?;
490
491        // Non-blocking reads
492        termios::set_read_mode(fd, 0, Duration::default())?;
493
494        // Ignore modem control lines (CLOCAL)
495        termios::ignore_carrier_detect(fd)?;
496
497        // Enable receiver (CREAD)
498        termios::enable_read(fd)?;
499
500        // Disable software flow control (XON/XOFF)
501        termios::set_software_flow_control(fd, false, false)?;
502
503        // Disable hardware flow control (RTS/CTS)
504        termios::set_hardware_flow_control(fd, false)?;
505
506        termios::set_line_speed(fd, baud_rate)?;
507        termios::set_parity(fd, parity)?;
508        termios::set_data_bits(fd, data_bits)?;
509        termios::set_stop_bits(fd, stop_bits)?;
510
511        // Pass through parity errors unfiltered
512        termios::set_parity_check(fd, ParityCheck::None)?;
513
514        // Flush the input and output queue
515        termios::flush(fd, Queue::Both)?;
516
517        Ok(Uart {
518            inner: UartInner {
519                device,
520                fd,
521                rtscts_mode,
522                rtscts_pins: None,
523                blocking_read: false,
524                blocking_write: false,
525                baud_rate,
526                parity,
527                parity_check: ParityCheck::None,
528                data_bits,
529                stop_bits,
530                software_flow_control: false,
531                hardware_flow_control: false,
532            },
533        })
534    }

663    /// Enables or disables XON/XOFF software flow control.
664    ///
665    /// When software flow control is enabled, incoming XON (decimal 17) and
666    /// XOFF (decimal 19) control characters are filtered from the input queue.
667    /// When XOFF is received, the transmission of data in the output queue is
668    /// paused until the external device sends XON. XOFF is automatically sent
669    /// to the external device to prevent the input queue from overflowing.
670    /// XON is sent when the input queue is ready for more data. You can also
671    /// manually send these control characters by calling [`send_stop`] and
672    /// [`send_start`].
673    ///
674    /// By default, software flow control is disabled.
675    ///
676    /// Support for XON/XOFF software flow control is
677    /// device-dependent. You can manually implement XON/XOFF by disabling
678    /// software flow control, parsing incoming XON/XOFF control characters
679    /// received with [`read`], and sending XON/XOFF when needed using
680    /// [`write`].
681    ///
682    /// [`send_start`]: #method.send_start
683    /// [`send_stop`]: #method.send_stop
684    /// [`read`]: #method.read
685    /// [`write`]: #method.write
686    pub fn set_software_flow_control(&mut self, software_flow_control: bool) -> Result<()> {
687        termios::set_software_flow_control(
688            self.inner.fd,
689            software_flow_control,
690            software_flow_control,
691        )?;
692
693        self.inner.software_flow_control = software_flow_control;
694
695        Ok(())
696    }

703    /// Enables or disables RTS/CTS hardware flow control.
704    ///
705    /// When hardware flow control is enabled, the RTS line (active low) is
706    /// automatically driven high to prevent the input queue from overflowing,
707    /// and driven low when the input queue is ready for more data. When the
708    /// CTS line (active low) is driven high by the external device, all data
709    /// in the output queue is held until CTS is driven low. You can also
710    /// manually change the active state of RTS by calling [`send_stop`] and
711    /// [`send_start`].
712    ///
713    /// When `Uart` is controlling a UART peripheral, enabling hardware flow
714    /// control will also configure the RTS and CTS pins.
715    ///
716    /// More information on hardware flow control can be found [here].
717    ///
718    /// By default, hardware flow control is disabled.
719    ///
720    /// Support for RTS/CTS hardware flow control is device-dependent. You can
721    /// manually implement RTS/CTS using [`cts`], [`send_stop`] and
722    /// [`send_start`], or by disabling hardware flow control and configuring
723    /// an [`OutputPin`] for RTS and an [`InputPin`] for CTS.
724    ///
725    /// [here]: index.html#hardware-flow-control
726    /// [`cts`]: struct.Status.html#method.cts
727    /// [`send_start`]: #method.send_start
728    /// [`send_stop`]: #method.send_stop
729    /// [`OutputPin`]: ../gpio/struct.OutputPin.html
730    /// [`InputPin`]: ../gpio/struct.InputPin.html
731    pub fn set_hardware_flow_control(&mut self, hardware_flow_control: bool) -> Result<()> {
732        if hardware_flow_control && self.inner.rtscts_pins.is_none() {
733            // Configure and store RTS/CTS GPIO pins for UART0/UART1, so their
734            // mode is automatically reset when Uart goes out of scope.
735            if let Some((rts_mode, cts_mode)) = self.inner.rtscts_mode {
736                let gpio = Gpio::new()?;
737
738                let (gpio_rts, gpio_cts) = if DeviceInfo::new()?.model() == Model::RaspberryPiBRev2
739                {
740                    // The Pi B Rev 2 exposes RTS/CTS through its (unpopulated) P5 header
741                    (GPIO_RTS_BREV2, GPIO_CTS_BREV2)
742                } else {
743                    // All other models with a 40-pin header use these GPIO pins
744                    (GPIO_RTS, GPIO_CTS)
745                };
746
747                let pin_rts = gpio.get(gpio_rts)?.into_io(rts_mode);
748                let pin_cts = gpio.get(gpio_cts)?.into_io(cts_mode);
749
750                self.inner.rtscts_pins = Some((pin_rts, pin_cts));
751            }
752        } else if !hardware_flow_control {
753            self.inner.rtscts_pins = None;
754        }
755
756        termios::set_hardware_flow_control(self.inner.fd, hardware_flow_control)?;
757
758        self.inner.hardware_flow_control = hardware_flow_control;
759
760        Ok(())
761    }

763    /// Requests the external device to pause its transmission using flow control.
764    ///
765    /// If software flow control is enabled, `send_stop`
766    /// sends the XOFF control character.

769    /// inactive state.

815    /// Sets the blocking mode for subsequent calls to [`read`].
816    ///
817    /// `min_length` indicates the minimum number of requested bytes. This
818    /// value may differ from the actual buffer length. Maximum value: 255
819    /// bytes.
820    ///
821    /// `timeout` indicates how long [`read`] blocks while waiting for
822    /// incoming data. `timeout` uses a 0.1 second resolution. Maximum
823    /// value: 25.5 seconds.
824    ///
825    /// [`read`] operates in one of four modes, depending on the specified
826    /// `min_length` and `timeout` values:
827    ///
828    /// * **Non-blocking read** (`min_length` = 0, `timeout` = 0). [`read`]
829    /// retrieves any available data and returns immediately.
830    /// * **Blocking read** (`min_length` > 0, `timeout` = 0). [`read`] blocks
831    /// until at least `min_length` bytes are available, or the provided buffer
832    /// is full.
833    /// * **Read with timeout** (`min_length` = 0, `timeout` > 0). [`read`]
834    /// blocks until at least one byte is available, or the `timeout` duration
835    /// elapses.
836    /// * **Read with inter-byte timeout** (`min_length` > 0, `timeout` > 0).
837    /// [`read`] blocks until at least `min_length` bytes are available, the
838    /// provided buffer is full, or the `timeout` duration elapses
839    /// after receiving one or more bytes. The timer is started after an
840    /// initial byte becomes available, and is restarted after each additional
841    /// byte. That means [`read`] will block indefinitely until at least one
842    /// byte has been received.
843    ///
844    /// By default, [`read`] is configured as non-blocking.
845    ///
846    /// [`read`]: #method.read
847    pub fn set_read_mode(&mut self, min_length: u8, timeout: Duration) -> Result<()> {
848        termios::set_read_mode(self.inner.fd, min_length, timeout)?;
849
850        self.inner.blocking_read = min_length > 0 || timeout.as_millis() > 0;
851
852        // If both read() and write() are non-blocking, we can safely set
853        // O_NONBLOCK once instead of toggling it for every write. We can't
854        // leave it set when read() should block, because it ignores the
855        // VMIN and VTIME settings.
856        if self.inner.blocking_read || self.inner.blocking_write {
857            unsafe {
858                libc::fcntl(self.inner.fd, libc::F_SETFL, 0);
859            }
860        } else {
861            unsafe {
862                libc::fcntl(self.inner.fd, libc::F_SETFL, libc::O_NONBLOCK);
863            }
864        }
865
866        Ok(())
867    }

869    /// Sets the blocking mode for subsequent calls to [`write`].
870    ///
871    /// [`write`] operates in one of two modes, depending on the specified
872    /// `blocking` value:
873    ///
874    /// * **Non-blocking write**. [`write`] returns immediately after
875    /// copying as much of the contents of the provided buffer to the output queue
876    /// as it's able to fit.
877    /// * **Blocking write**. [`write`] blocks until the entire contents of the provided buffer
878    /// can be copied to the output queue. If flow control is enabled and the
879    /// external device has sent a stop request, the transmission of any waiting data
880    /// in the output queue is paused until a start request has been received.
881    ///
882    /// By default, [`write`] is configured as non-blocking.
883    ///
884    /// [`write`]: #method.write
885    pub fn set_write_mode(&mut self, blocking: bool) -> Result<()> {
886        self.inner.blocking_write = blocking;
887
888        // If both read() and write() are non-blocking, we can safely set
889        // O_NONBLOCK once instead of toggling it for every write. We can't
890        // leave it set when read() should block, because it ignores the
891        // VMIN and VTIME settings.
892        if self.inner.blocking_read || self.inner.blocking_write {
893            unsafe {
894                libc::fcntl(self.inner.fd, libc::F_SETFL, 0);
895            }
896        } else {
897            unsafe {
898                libc::fcntl(self.inner.fd, libc::F_SETFL, libc::O_NONBLOCK);
899            }
900        }
901
902        Ok(())
903    }

915    /// Receives incoming data from the external device and stores it in
916    /// `buffer`.
917    ///
918    /// `read` operates in one of four (non)blocking modes, depending on the
919    /// settings configured by [`set_read_mode`]. By default, `read` is configured
920    /// as non-blocking.
921    ///
922    /// Returns how many bytes were read.
923    ///
924    /// [`set_read_mode`]: #method.set_read_mode
925    pub fn read(&mut self, buffer: &mut [u8]) -> Result<usize> {
926        self.inner.device.read(buffer).or_else(|e| {
927            if e.kind() == io::ErrorKind::WouldBlock {
928                Ok(0)
929            } else {
930                Err(Error::Io(e))
931            }
932        })
933    }
934
935    /// Sends the contents of `buffer` to the external device.
936    ///
937    /// `write` operates in either blocking or non-blocking mode, depending on the
938    /// settings configured by [`set_write_mode`]. By default, `write` is configured
939    /// as non-blocking.
940    ///
941    /// Returns how many bytes were written.
942    ///
943    /// [`set_write_mode`]: #method.set_write_mode
944    pub fn write(&mut self, buffer: &[u8]) -> Result<usize> {
945        // We only need to toggle O_NONBLOCK when read() is configured as
946        // blocking. If read() is non-blocking, either with_path() or
947        // set_read_mode() will have already enabled O_NONBLOCK.
948        if self.inner.blocking_read && !self.inner.blocking_write {
949            unsafe {
950                libc::fcntl(self.inner.fd, libc::F_SETFL, libc::O_NONBLOCK);
951            }
952        }
953
954        let result = self.inner.device.write(buffer).or_else(|e| {
955            if e.kind() == io::ErrorKind::WouldBlock {
956                Ok(0)
957            } else {
958                Err(Error::Io(e))
959            }
960        });
961
962        if self.inner.blocking_read && !self.inner.blocking_write {
963            unsafe {
964                libc::fcntl(self.inner.fd, libc::F_SETFL, 0);
965            }
966        }
967
968        result
969    }
